# ADR-0006 — Retry de mineração e compatibilidade de fachadas

- **Status:** Implementada; fachada é transitória.
- **Pesquisa:** `ContestResearchTriggerAdapter` executa `MineContestPatternsService.mine()` sincronamente. A falha é capturada pelo adapter e reportada por `false`; não desfaz a persistência nem altera 201/200. `RegisterContestHandler` solicita pesquisa em todo POST válido, inclusive repetição idempotente. Isso permite reprocessar falha passada sem inserir novo concurso. O miner usa idempotência versionada por faixa, então um run completo não é regravado. Importação CSV chama o trigger uma única vez após lote concluído com inserções novas; não roda mineração para cada linha ou em lote abortado.
- **Durabilidade:** a solicitação manual de pesquisa não é uma mensagem durável. O projeto tem execução agendada periódica como recuperação adicional; um request cuja chamada síncrona falhe pode ser tentado novamente em novo POST. Não introduzir outbox/job nesta fase porque mudaria o comportamento operacional e o requisito atual foi preservar o acionamento síncrono.
- **Timeout:** não há timeout independente para a mineração síncrona; uma execução lenta pode alongar a resposta. Medir e rever se latência se tornar requisito.
- **Fachadas preservadas:** `application.RegisterContestService`, `GetContestService`, `GetLatestContestService` e `ListContestsService` ficam como adaptadores que convertem chamadas antigas para as portas de entrada do módulo. A lógica real reside nos handlers do feature `contests`.
- **Critério de remoção:** remover essas fachadas e `application.port.ContestRepository` após (a) `rg` confirmar que produção e testes não têm clientes além da configuração/adapter de compatibilidade, (b) todos os consumidores migrados às portas de entrada e (c) um ciclo de integração sem consumidores antigos. O arquivo de dump textual `src/main/fontes_projeto.txt` não é consumidor compilado; deve ser regenerado/revisado separadamente. Não remover automaticamente nesta fase.
